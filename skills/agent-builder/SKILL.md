# Agent 构建器

为任意领域构建 AI 智能体：客服、研究、运营、创意工作或特定业务流程都适用。

## 核心哲学

> **模型本来就知道如何成为智能体。你的工作是不要妨碍它。**

智能体并不等于复杂工程。它本质上是一个很简单的循环，让模型有机会行动：

```
LOOP:
  模型看到：上下文 + 可用能力
  模型决策：行动或回应
  若行动：执行能力，写回结果，继续循环
  若回应：返回给用户
```

**就这么简单。** 魔法不在代码里，而在模型里。你的代码只是提供机会。

## 三个核心要素

### 1. 能力（它“能做什么”？）

智能体可执行的原子动作：搜索、读取、创建、发送、查询、修改。

**设计原则**：先从 3-5 个能力开始。只有当智能体稳定失败且明确缺某能力时，再增加能力。

### 2. 知识（它“知道什么”？）

按需注入的领域知识：政策、流程、最佳实践、数据结构。

**设计原则**：让知识“可用”，而非“强塞”。在相关时加载，不要一开始全部灌入。

### 3. 上下文（“发生过什么”？）

对话历史，是把动作串成连贯行为的主线。

**设计原则**：上下文很宝贵。把噪声子任务隔离掉，截断冗长输出，保护清晰度。

## 智能体设计思维

在动手前，先想清楚：

- **目标**：这个智能体最终要完成什么？
- **领域**：它工作在哪个世界？（客服、研究、运营、创作……）
- **能力**：哪 3-5 个动作是刚需？
- **知识**：它需要接入哪些专业知识？
- **信任边界**：你愿意把哪些决策交给模型？

**关键点**：信任模型。不要过度工程化，不要预先写死流程。给能力，让它推理。

## 渐进式复杂度

先简单，只有在真实使用暴露问题时再加复杂度：

| 层级 | 增加什么 | 何时增加 |
|-------|----------|----------|
| 基础 | 3-5 个能力 | 永远从这里开始 |
| 规划 | 进度跟踪 | 多步骤任务出现失焦 |
| 子智能体 | 上下文隔离子代理 | 探索过程污染主上下文 |
| 技能 | 按需知识加载 | 需要领域专业知识 |

**大多数智能体都不需要超过第 2 层。**

## 领域示例

**业务场景**：CRM 查询、邮件、日程、审批  
**研究场景**：数据库检索、文档分析、引用整理  
**运营场景**：监控、工单、通知、升级处理  
**创意场景**：素材生成、编辑协作、评审迭代

模式是通用的，变化的只是能力集。

## 关键原则

1. **模型就是智能体本体**：代码只负责跑循环
2. **能力提供行动边界**：定义“它能做什么”
3. **知识提供判断依据**：定义“它知道怎么做”
4. **约束帮助聚焦**：边界越清晰，行为越稳定
5. **信任释放能力**：让模型做推理，不要替它写死
6. **迭代揭示需求**：先最小可用，再按使用反馈进化

## 反模式（Anti-Patterns）

| 反模式 | 问题 | 解决方式 |
|--------|------|----------|
| 过度工程化 | 需求未出现就引入复杂结构 | 从简单开始 |
| 能力过多 | 模型决策混乱 | 初期控制在 3-5 个 |
| 工作流刚性 | 无法适配新情况 | 让模型自己决策 |
| 知识前置灌入 | 上下文膨胀 | 按需加载 |
| 过度微操 | 抑制模型智能 | 信任模型 |

## 智能体思维方式

**从**：“我怎么让系统执行 X？”  
**到**：“我怎么让模型有能力完成 X？”

**从**：“这个任务流程是什么？”  
**到**：“完成这个目标需要哪些能力？”

最好的智能体代码往往朴素到近乎无聊：简单循环、清晰能力、干净上下文。魔法不在代码本身。

**给模型能力与知识，然后信任它完成剩下的部分。**
